# 四条保证

Custos 要求你把交易所凭据交给它。让这件事变得合理的，是下面四条性质。它们不是特性、也不是默认值 —— 无论部署要求什么，它们都成立，而且每一条都在不止一处强制，好让单点失误无法把它抹掉。

| # | 保证 | 一句话 |
|---|---|---|
| 1 | [密钥不出本机](./keys-never-leave-the-host) | 解密密钥从不被传输、记录或发布。 |
| 2 | [live 执行始终受门控](./live-execution-is-gated) | 抵达 live 交易所需过四道校验，且门是 fail closed 的。 |
| 3 | [失联时安全防护依然生效](./safety-survives-disconnect) | 平台不可达时，本地强制继续工作。 |
| 4 | [金额运算精确](./exact-money-arithmetic) | 全程 decimal，wire 上是字符串，不用浮点。 |

## 为什么是这四条

每一条都堵住了一种"系统可能背叛你、而你来不及察觉"的方式。

**密钥**。托管式服务被攻破一次，就可能同时丢掉所有人的凭据。Custos 不会：凭据在你的机器上，解密它的密钥也在你的机器上。攻破平台拿到的是部署元数据，不是你的资金。

**门控**。一笔 live 订单被投给"悄悄什么都不做"的 host，看起来和成功下单一模一样。你会在对账时才发现，而那太晚了。所以这道门选择拒绝，而不是降级。

**失联**。两种相反的失败都是真实的：因为一次网络抖动就平掉没人要求平的仓；或者在没人盯着的时候恰好取消了防护。runner 两者都不做。

**金额**。名义敞口计算里的浮点误差不会自己报警。它给出一个几乎正确、经得起肉眼检查、但朝着舍入方向错了的数。decimal 运算直接消除了这一类问题。

## 它们如何被强制

每条保证都有不止一个强制点。凭据的 scope 在写入时校验**并且**在每次解密时再校验；门控是能力声明**加上**交易所校验**加上** code hash**加上**凭据 scope。

这是刻意的。单一强制点距离被绕过只有一次重构，而绕过在出事之前是看不见的。
