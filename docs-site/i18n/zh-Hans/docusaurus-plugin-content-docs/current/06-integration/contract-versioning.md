# 契约版本化

只有一个版本。V1 就地演进。

政策就这一句，而且它比多数版本方案都更窄 —— 这是有意的。下面讲的是它在实践中意味着什么，以及要出现第二个版本需要先成立哪些事实。

## 为什么不并行跑两个版本

兼容路径意味着同一条消息有两个解析器。两个解析器意味着两种行为，而它们之间的差异，只会由那条恰好走中"你没测过的那一个"的消息暴露出来。对一份**授权用真金白银下单**的契约来说，用这个风险换一次更从容的灰度，并不划算。

所以这里没有前代解析器、没有兼容别名、也没有协商步骤。runner 只接受一种形状；认不出来就拒绝，而不是去猜。

## "就地演进"的代价

每一份 schema 都是 `additionalProperties: false`，这让两类改动都必须协同：

| 改动 | 效果 |
|---|---|
| 新增可选字段 | 在所有消费者升级完之前，生产方不能发送它 —— 未升级的消费者会拒绝这个未知键，而不是忽略 |
| 新增必填字段 | 未升级的生产方立即校验失败 |
| 删除或重命名字段 | 两侧一起动，否则都不动 |

注意这里的"可选"买到的东西比通常少。在 `additionalProperties: true` 之下，新增可选字段是一次免费的单边改动；在 `false` 之下，它仍然要求两侧都已部署。而正是这份严格，让未知字段成为一个**被发现的错误**，而不是一次**静默的丢弃** —— 在这里，后者的价值远高于轻松的灰度。

## 为什么改动是重新签发而不是编辑

若干契约资产被仓库的权威索引按 path、size 与 commit 记录在案，fact batch 的 schema 还额外带一份摘要 sidecar。改动其中任何一个文件，都会让"当初签的是什么"这条记录失效。

因此一次契约改动是：更新 schema、更新 golden、更新摘要、重新签发回执。缺任何一环都是断裂的证据链，而测试套件会把它报成失败，不是警告。这是刻意设置的摩擦 —— 它让契约改动的代价在有人提出它的那一刻就是可见的。

## V2 需要什么

两件事，而且都不是我们单方面能决定的：

1. **一个真实的外部生产消费者**，且已钉住 V1 的精确字节。
2. **一个提前声明的迁移窗口**。

今天没有任何消费者回执被钉住。仓库里每一份回执都处于 open 或 pending 状态 —— 生产侧已完成，独立的消费方验收尚未完成。所以 V2 目前不可用；这是一个关于**证据**的陈述，而不是关于偏好的：没有消费者钉在 V1 上，V2 就没有可迁移的**来处**。

空的 `v2`、`v3`、`v4` 目录是占位符。它们的存在不构成计划，把它们读成路线图是一个值得避免的误解。

## 两个不同的时钟

包版本与契约版本各走各的：

- **包 SemVer** —— `custos-runner` 的发布、EOL 窗口、安全补丁。见
  [SemVer 与 LTS](/zh-Hans/release-governance/semver-lts)。
- **契约版本** —— `v1`，以及本页的规则。

一次 MINOR 包发布可以携带一次 V1 改动，而一次 MAJOR 包发布并不意味着 V2。把版本号跳变读成契约事件（或者反过来），是误读发布说明最可能的方式。

## 弃用

V1 内部没有弃用机制，因为没有可以弃用**到**的地方 —— 一个字段要么在契约里，要么不在。删除字段就是一次契约改动，按上面的方式处理。

如果这听起来不够灵活：确实如此。这个设计"灵活"的那个版本，是生产方与消费方对某个字段是否还是原来的含义各执一词，而双方都要等到某一笔成交出错时才发现。
